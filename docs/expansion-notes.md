## 1. 기본 방향

- **POS와 키오스크는 같은 API를 쓰고 UI만 다르다.** 둘 다 "상품을 장바구니에 담고 → 결제하고 → 판매가 생긴다"는 흐름이 같다
  - POS: 바코드를 스캔하면 그 상품이 담긴다
  - 키오스크: 메뉴를 터치하면 그 상품이 담긴다. 카페 음료·디저트도 **상품번호를 체번**해 같은 상품 마스터(`PRODUCT`)로 관리
- **카페 키오스크는 선불**이다: 키오스크에서 주문 입력과 결제를 한 번에 하고, 주문 후 고객이 수령한다 (후불·테이블 주문 아님). 그래서 지금의 `checkOut`(카트 → 판매 + 결제를 한 번에 저장) 흐름을 그대로 쓸 수 있다
- **ERP는 POS·키오스크가 만든 판매 데이터를 원재료로 쓴다.** 그래서 ERP 전에 판매 데이터에 빠진 값(3장)을 채워야 한다
- 이번 API 변경에서 키오스크를 위해 미리 한 것: 경로를 자원 단위로 재설계 (`/api/carts`, `/api/sales`, `/api/products`). 나머지 키오스크 기능은 **기존 API를 깨지 않고 추가**할 수 있어서 지금 하지 않는다

## 2. 카페 키오스크 단계에서 할 것

| 항목 | 지금 상태 | 필요한 것 | 비고 |
|---|---|---|---|
| 상품 ID로 담기 | 담기는 `barcode`만 받음 | 담기 요청에 `productId`도 받기 (바코드·상품 ID 중 하나) | POS는 계속 바코드를 보내므로 영향 없음. A6의 `barcode @NotBlank`를 "둘 중 하나 필수"로 바꿈 |
| 메뉴 목록 | 없음 (`ProductController` 빈 자리, 경로는 `/api/products`) | 카테고리별 상품 목록 조회 (판매 가능 상품만, 정렬·이미지 등) | 판매중지(`discontinued`) 제외 규칙은 담기와 같게 |
| **옵션** | 없음. `Cart`는 **같은 바코드면 수량을 합침** (`Cart.addOrIncrease`) | 옵션 마스터(사이즈, 샷 추가, 시럽 등)와 추가 금액. **같은 상품이라도 옵션이 다르면 다른 라인** — 라인을 묶는 기준이 "바코드" → "상품 + 옵션 조합"으로 바뀜 | 사용자 의견: "옵션만 특별하게 처리". 라인 금액 = (단가 + 옵션 금액) × 수량. `SALE_LINES`에 옵션 저장 방식(별도 테이블 / JSON) 결정 필요 |
| **카드 결제** | 미구현 (`UnsupportedPaymentMethodException`, A4 이후 400) | 카드 승인 흐름. 키오스크는 현금을 받지 않으므로 **사실상 전제 조건** | 실제 VAN/PG 연동 대신 모의 승인으로 시작할지 결정. `CARD_PAYMENTS` 테이블, L5(결제 수단별 저장 정책), B17(enum ↔ CHECK) 함께 정리 |
| 대기 번호·수령 | 없음 | 주문 번호 발급, 상태(접수 → 제조 중 → 완료 → 수령), 호출 화면용 조회 | 결제는 이미 끝난 뒤라 판매(`SALES`)와 별도의 "주문 진행 상태"로 둘지 결정 |
| 계산원 | `"테스터"` 고정 (B14b 보류) | 키오스크는 계산원이 없음 → 계산원 nullable 또는 기기 ID | 3장 데이터 보강과 함께 |
| 채널 구분 | 없음 | 판매가 POS에서 왔는지 키오스크에서 왔는지 (`SALES.CHANNEL` 등) | 3장 |
| 장바구니 저장 | 인메모리 `ConcurrentHashMap` (서버 재시작 시 사라짐) | 선불이라 장바구니 수명이 짧아 **당장은 인메모리로 충분**. 서버를 여러 대로 늘리면 DB·Redis로 이전 | |
| 반품 | 전체 반품만 | 카페는 부분 취소(한 잔만 취소)가 많을 수 있음 | 필요해지면 별도 설계 |

## 3. 판매 데이터 보강 (키오스크와 함께 또는 직전)

지금 저장하지 않는 값은 나중에 복원할 수 없다. ERP 전에 반드시 채운다. 모두 **스키마 변경**이라 운영 DB 마이그레이션이 필요하다.

| 값 | 지금 | 왜 필요한가 |
|---|---|---|
| 판매 라인의 상품 ID (`SALE_LINES.PRODUCT_ID`) | 없음 — 바코드만 저장 (반품 재입고도 바코드로 처리, `SaleRowMapper.getCartLine`이 `productId(null)`) | 바코드는 바뀌거나 재사용될 수 있음. ERP의 상품별 집계·원가 계산 기준 |
| 계산원 / 기기 | `"테스터"` 고정 (`Sale.java:50`) | 직원별 매출·정산, 키오스크 기기별 매출 |
| 채널 | 없음 | POS / 키오스크 매출 구분 |
| 옵션 | 없음 | 옵션별 매출, 원재료 차감 |
| 원가 | 없음 | 매출 총이익 (ERP) |

## 4. ERP 단계 (POS·키오스크 완성 후)

| 영역 | 지금 | 필요한 것 |
|---|---|---|
| 재고 | `INVENTORY.STOCK` 숫자만 바꿈 (`decreaseStockByBarcode`) — **이력이 남지 않음** | 입출고 원장(판매·반품·입고·폐기·재고 조정이 각각 한 행) + 현재고는 원장 합계 또는 스냅샷 |
| 매입 | 없음 | 발주·입고·거래처 |
| 점포·기기 마스터 | 없음 (`strCd`·`posNo`는 문자열만) | 점포, POS/키오스크 기기 등록 |
| 정산 | 없음 | 일 마감, 결제 수단별 집계, 계산원별 시재 |
| 상품 마스터 관리 | 조회만 | 등록·수정, 가격 이력, 카테고리·브랜드 관리 (스키마 문제점 `schema-issues.md` 1~6번 정리 포함) |
| 구조 | 단일 Spring Boot 앱 | POS 코어와 ERP를 모듈(또는 서비스)로 나눌지 결정. ERP는 판매 데이터를 **읽기만** 하는 쪽부터 시작하는 게 안전 |

## 5. 단계를 시작하기 전에 정할 것

| 시점 | 결정 |
|---|---|
| 키오스크 시작 전 | 카드 결제 방식 (모의 승인 / 실제 연동), 옵션 저장 구조, 주문 진행 상태를 판매와 분리할지, 3장 데이터 보강을 같이 할지 |
| 키오스크 또는 ERP 시작 전 | **DB를 PostgreSQL로 옮길지** — 기기가 늘고 ERP가 붙으면 SQLite의 쓰기 직렬화가 한계 (`bugfix-plan.md` 9장에 전환 시 바뀌는 점 정리) |
| ERP 시작 전 | 모듈 분리 방식, 재고 원장 구조, 점포·기기 마스터 |

## 6. 지금 하지 않는 이유

- 키오스크 항목은 대부분 **기존 API에 더하는 것**(새 엔드포인트·필드·결제 수단)이라, POS를 먼저 완성해도 다시 깨지 않는다. 깨지는 결정(URL 구조)만 이번에 했다
- 옵션·카드 결제·재고 원장은 도메인 모델을 바꾸는 큰 작업이라, 지금 API 변경 단계에 넣으면 범위가 몇 배로 커진다
- 실제로 시작할 때는 요구사항이 바뀌어 있을 가능성이 크므로, 지금은 방향만 고정하고 세부 설계는 그때 한다
